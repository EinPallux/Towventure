- **Phase 3 — The Living Tower (in progress):** the multiplayer systems.
  - **Slice G — seasons data model & the rollover job (GDD §11, BALANCE §7).** The competitive clock. A `seasons` table carries the 8-week window + status for the end-date UI; Honor stays in the already-seasoned ledger. **Placement math** is live exactly as authored: `placementHonor(finalHonor) = round(√finalHonor × 12)` — a Crownseeker (5000) is compressed to ~849 (Gatekeeper+), never back to zero. **The rollover job** (`runSeasonRollover`) compresses every account's ending-season total into a single `placement` ledger row in the new season, marks the old season ended, opens the new one, and is idempotent (it refuses to double-place a season that already has placement rows) — so it can be rehearsed as a restore drill before the first real rollover runs from ops in Phase 5. **Lifetime Honor** (never resets) is the sum of earned ledger deltas across all seasons *excluding* placement carry-overs, surfaced on `/api/me` and in the ladder header. New route `GET /api/season` (window + your standing + projected next-season placement + lifetime); the Ladder shows the season number, days remaining, and your reset preview. Migration `0009_seasons.sql`. Verified: 22 server integration tests (placement math; a two-account rollover writing the compressed seeds with lifetime excluding them + the idempotent guard; the season endpoint) green; goldens untouched. **This completes Phase 3's scope — Echoes, Skirmishes, the Honor economy + Merchant + Vault, ladder variety, the Daily Gauntlet, friends/feed/inbox + live toasts, and seasons are all live end-to-end; staging-VPS exit criteria remain to be checked on a live deploy.**
  - **Slice F — friends, the feed, the inbox & live toasts (GDD §10).** The social scaffolding that makes the tower feel inhabited. **Friends:** request by name (case-insensitive), accept, list — one edge per pair, an accepted edge counting both directions, and a request auto-accepts when the target already asked you (`friendships` table; `POST /api/friends/request|accept`, `GET /api/friends` with incoming/outgoing pending). **The feed** (`feed` table): each account's milestones — reaching every 10th floor, forging a Zenith (★5), and your Echo slaying a challenger — are emitted in the causing transaction; `GET /api/feed` returns the union of your and your friends' recent events. **Profiles:** `GET /api/profile/:name` — the Hall of Echoes header (tier, season Honor, the account's own Echo + kill count). **Inbox:** `GET /api/me/inbox` now reports an unread count, `POST /api/me/inbox/read` clears it. **Live toasts** ship as **Server-Sent Events** rather than a WebSocket (no new dependency; the browser's `EventSource` carries the session cookie same-origin): an in-process pub/sub bus (`services/bus.ts`) is subscribed per account by `GET /api/stream`, and emit points publish *after commit* (so a rolled-back transaction never false-toasts) — an Echo kill nudges the dead owner, a floor/Zenith milestone nudges the climber and their friends. Durable truth stays in the inbox/feed rows; the stream is only the live nudge. The client gains a Friends & Feed screen (add/accept, friends list with tiers, the feed, the inbox — marked read on open), a top-bar Friends button with an unread badge, and floating live toasts wired to the SSE stream (opened on bootstrap, closed on logout). Migration `0008_social.sql`. Verified: 19 server integration tests (request→accept→friends-see-each-others'-feed; inbox unread + mark-read; the live bus delivers to subscribers and stops after unsubscribe) green; goldens untouched. (SSE replaces WS because no `ws`/`@fastify/websocket` is vendored; the streaming endpoint itself isn't inject-tested, but the bus + emit points are.)
  - **Slice E — ladder variety & the Daily Gauntlet (GDD §10).** The Stairs get four boards, and the tower gets a shared daily challenge. **Ladders:** one generic `rankedPage` (a `rank() OVER (ORDER BY value DESC)` window with an off-page pinned self-row) now drives **Global** (season Honor), **the Unnumbered** (top-100 by Honor), **Weekly Climb** (best floor on runs started since Monday 00:00 UTC), and **Echo Kills** (climbers each account's Echo has slain) — each paginated, metric-labelled (Honor/Best Floor/Echo Kills), with tier badges only on the Honor boards. The client Ladder gains board tabs and metric-aware columns. **Daily Gauntlet:** a shared-seed, class-rotating run everyone plays identically today — the seed (FNV-1a of the UTC day number) and forced class (vanguard → duelist → arcanist rotation) are a pure function of the day, so two accounts get bit-identical doors/shops/loot (the determinism the run layer already guarantees), verified by a test that starts the Gauntlet on two accounts and asserts equal seed + class + doors. No boons, no vows — the shared run is fair. It's a normal run thereafter (played through the run routes), tagged `gauntlet_day` for its own daily best-floor ladder; a second entry the same day is refused. New routes `GET /api/gauntlet` (today's seed/class/ladder/entered-flag) + `POST /api/gauntlet/start`, four `GET /api/ladders/*` boards, and a Gauntlet panel on the Gate. The UTC-close Honor-pot payout is a rollover job (ships with Slice G). Migration `0007_gauntlet.sql`. Verified: 16 server integration tests (two-account Gauntlet determinism + same-day block; all four ladder boards respond with the right metric; Unnumbered caps at 100) green; goldens untouched.
  - **Slice D — the Honor Merchant, Marks sinks & the Vault of Champions (GDD §10.2, CONTENT §8).** Valor Marks (from Echo bounties + Skirmishes) finally spend. Two shelves plus a gated third: **War Chest boons** — the *only* gameplay purchase, deliberately mild, one armed per run (Heavy Purse +50 gold, Wide Straps +2 backpack, Traveler's Kit a starter Whetstone) — arm one at the Merchant and it fires at your next run's start; **cosmetics** (weapon trails, Echo auras, banners, titles) bought with Marks and owned forever (prestige flags until the Phase 4 art pass); and the **Vault of Champions**, gated by 3 Champion's Keys (from Skirmish wins), stocking a season-exclusive aura and *War Chest Prime* (+100 gold and +2 slots — the best boon, still mild). Boon effects (`run/boons.ts applyBoon`) touch only gold/backpack/starting inventory — never combat stats — so the golden suite is untouched; the server consumes the armed boon in the run-start transaction. Purchases move Marks via ledger rows (a `buy:<id>` debit, affordability re-checked inside the transaction so a spend never drives the balance below zero) or spend 3 Keys (marked on the skirmish rows that granted them); cosmetics land in an `unlocks` table (owned once), boons arm on `accounts.armed_boon`. New routes `GET /api/merchant` (catalogue with owned/armed/affordable flags) + `POST /api/merchant/buy`; a Merchant screen with boon/cosmetic/Vault shelves; migration `0006_merchant.sql`. Verified: 163 shared + 14 server tests (boon effects; buy-a-cosmetic-then-arm-a-boon-with-Marks with the boon firing +50 gold at run start and consuming; 3 Keys buy a Vault item and a fourth attempt is refused) green; goldens untouched.
  - **Slice C — Skirmishes end-to-end (GDD §9, free async PvP).** From the top bar, anytime, no run required: attack a rival's defense snapshot and watch the duel like a bet. **Defense snapshots** auto-forge on run start and upgrade at each boss kill (`defenses` table, one per account) — so every account that has climbed is attackable, risk-free (defenders can't decline and never lose anything). **The Rival Board** offers up to three opponents around your Honor — one below, one even, one above (the *above* pick pays best). **Tickets** gate attacks: 5/day, +1 at Honor tier rank 4, +1 more at rank 6; the same defender is attackable at most once/day. **The duel** is `buildDuelSpec(yourDefense, theirDefense)` through the same deterministic sim, server-seeded; the client re-sims from both builds + the seed to render a full 1v1 replay with a win/loss + Honor banner. **Stakes** (BALANCE §6): the attacker's Honor moves Elo-style (K=24, `E = 1/(1+10^((H_def−H_att)/400))`, season Honor floored at 0), the **defender only ever gains** — a successful defense (you lost) pays them +8 Honor + 10 Marks. Winning vs an equal-or-higher rival (`H_def ≥ H_att − 50`) drops a **Champion's Key** (3 open the Vault — spend lands in Slice D). **Anti-farm:** repeat wins over the same account this rolling week decay the Honor gain ×1 → ×0.5 → ×0.25 → 0. The Elo/decay math is server-only (a one-shot economy calc using floats — never replayed or hashed, so the deterministic run layer stays float-free); every Honor/Mark movement is a ledger row in the fight transaction, backed by the `skirmishes` attack ledger (which also drives tickets, the once/day guard, decay, and the Key tally). New routes `GET /api/skirmish` (board + tickets + keys) and `POST /api/skirmish/attack`; migration `0005_skirmish.sql`. Verified: 12 server integration tests (Elo/ticket/decay math exact; beating a weak rival wins Honor + a Key + is blocked on repeat; losing to a strong wall pays the risk-free defender) green; goldens untouched (duel reuses existing specs); harness unaffected.
  - **Slice B — Echoes end-to-end (GDD §8, the signature system).** Other players become content: die and your build is snapshotted as an **Echo** that haunts your death floor for every climber after you. **Death → Echo:** any run that dies upserts one `echoes` row (the `HeroBuild` snapshot, floor, owner Honor; one per account, a new death replaces the old — trap-corpse builders get a real choice). **Placement:** the server injects an Echo door into a live run near a matching corpse — at most one per 5 floors, never before floor 3, never the sole path (it replaces a battle door only when another remains); candidates within ±5 floors, freshest first, with a **house Echo** ("The Sleepwalker") seeding floors 6–12 for onboarding when no real corpse fits. **The fight is just a fight:** choosing the door duels the dead player's build through the same deterministic sim (`buildDuelSpec(snapshotOf(hero), echo.build, echo.bonusPct)`), so the client re-sims to the identical hash; the Echo gets a staleness-decayed fury bonus (+10% fresh → 0 over 5 days). **Rewards, both sides:** a kill pays the hunter an Honor bounty (`12 + 1.1×floor + 25×tier-gap`, halved punching ≥2 tiers down) + Marks + a **Grave-Copy** (pick 1 of 3 of the Echo's items as a ★1 copy, or forfeit and climb on) — all honor/marks as ledger rows in the fight transaction; a defense win credits the *dead owner* a +3 Honor / +6 Marks trickle, tallies the kill, and drops an **inbox** notification ("Your Echo on Floor 61 has slain Kess."). Lifecycle: an Echo fades after 3 defeats or 14 days. The Gate's top bar shows your Echo's live kill count; the death ritual names the Echo that felled you ("Maro's Echo put you down"); `/api/me` returns your own Echo, `GET /api/me/inbox` the notifications. Forward-only migration `0004_echoes.sql` (echoes + inbox tables). Verified: 162 shared tests (Echo economy math, duel determinism, grave-copy claim/forfeit, death-by-Echo) + 9 server integration tests (the two-sided ledger economy is exact; a real corpse is injected near a hunter and the duel resolves end-to-end over HTTP) green; goldens untouched (Echoes are run-layer + server, no engine change); harness curve unchanged (Echo doors are server-injected, never seen by the greedy climber).
  - **Slice A — the duel primitive, the Marks ledger, and Honor-tier unlocks (GDD §7, §8, §10.2).** The foundation the async-multiplayer systems stand on. **A duel is just a fight:** `HeroBuild` names the minimal build slice `buildHeroSpec` reads (class, floors, equipment, vows); `snapshotOf` captures exactly that slice and `buildDuelSpec(attacker, foe, foeBonusPct)` turns two snapshots into a `CombatSpec` — the foe placed as enemy `e0`, an optional fight-start damage buff modelling the Echo's staleness-scaled aggression — so an Echo/Skirmish reuses the same deterministic sim the tower already runs (`buildHeroSpec`/`tagCounts` now take a `HeroBuild`, not a whole `RunState`). **Valor Marks** get their ledger: a `marks_ledger` table (the soft-currency twin of `honor_ledger`, season balance = SUM(delta), earnings positive, Merchant spend negative) with `seasonMarks`/`awardMarks` services, forward-only migration `0003_marks.sql`; `/api/me` now returns `marks` and the 0-based `tierRank`. **Honor-tier class unlocks** go live: `honorTierRank(honor)` maps season Honor to a tier rank, `/api/run/start` refuses a class whose `unlockTier` exceeds it (403, Vanguard rank-0 always open, Duelist at Gatekeeper, Arcanist at Vaultbreaker), and the Gate greys out locked classes with a "🔒 unlocks at <tier>" label; the top bar shows the Marks balance. Verified: 153 shared tests (duel-primitive determinism + tier-rank thresholds) and 7 server integration tests (fresh account gated to Vanguard, marks default 0) green; goldens untouched (the duel builder composes existing specs, no engine change).

  - **Infusion sockets — materials socket into gear (GDD §4.2, CONTENT §3.5):** the second half of item progression alongside fusion. Items carry infusion sockets by rarity (Common 0 · Uncommon 1 · Rare 2 · Epic/Mythic 3); a new `infuse` command sockets a backpack material into a backpack-or-equipped item — appending to a free socket or overwriting an existing one (which permanently destroys the old infusion) — and consumes the material. `run/build` compiles a socketed item's material mods/effects into the hero, so Leadweave's +8 Armor/−3% Speed or Emberdust's 15% OnHit-Burn actually reach combat. **Fusing keeps the better socket set** (the copy with more infusions survives), so "infuse now or wait for ★3?" is a real decision (GDD §4.2). Seven materials are functional — Whetstone (+6% weapon damage, modelled as a fight-start damage buff), Emberdust, Frostmote, Leadweave, plus new **Hollowfang** (+4% Lifesteal) and **Glimmergrit** (+5% Crit), and Blood-Amber; the rest await their systems (Echo/Skirmish, Every-interval op). Materials are shop-stocked and now render legibly; the client backpack shows socket pips (◈/◇) on every item and offers an Infuse action. Determinism/goldens untouched (sockets only shape the compiled build); 5 run tests cover infuse, capacity, overwrite, fuse-keeps-better, and build compilation.
  - **Consumables auto-fire in combat (CONTENT §3.4):** the 5 anchor consumables now do something. Each held consumable compiles into a **one-shot hero effect** for the fight, firing on a player-set condition — fight start / HP<70% / HP<40% / Doomfall / vs Elite+ — mapped to the matching sim trigger (`vsElite` only compiles when the roster has an elite or boss). The sim tracks which one-shots fired (`SimResult.firedOneShots`, from a new `EffectBinding.oneShotId`) and the run layer **spends exactly those** — so an emergency Small Ale that never triggered is kept, not wasted. A new `setConsumableCondition` command (validated, server-authoritative, compile-time parity-guarded) lets players retarget the condition; the client backpack grows a condition dropdown and finally renders consumables legibly (name, effect, ⚗ marker) instead of a raw id. Determinism holds end-to-end: the client re-sims from the pre-fight state, whose backpack still holds the consumables, so its bindings match the server's exactly.
